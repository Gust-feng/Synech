# 产品能力装配与新功能开发规则

> 本文规定 Synech v1 如何把基础能力组合成新的产品能力。产品层使用“能力”描述用户可获得的行为；工程层仍使用 Feature、Application、Coordination、Adapter 和 Projection 表达责任边界。本文固定长期契约，不规定每个能力的内部实现。

## 1. 目标

新能力必须能够在不继续扩大 `PanelHost`、`request-handler` 和顶层 UI 状态的前提下接入。

稳定事实由唯一的 Feature owner 拥有；完整业务动作由 Application 拥有；跨 Feature 生命周期由 WorkbenchCoordination 拥有；HTTP、Agent、Desktop 和未来 CLI 只属于 Adapter。一个业务动作只能有一个 canonical command path，多个入口只能是薄适配器，不能各自实现一套语义。

## 2. 能力角色

一个产品能力按实际需要声明以下角色，不要求机械创建同名文件。角色不适用时明确标记为“不适用”，不得用空实现满足目录形式。

### Feature：事实 owner

Feature 拥有一个长期事实及其 Repository port，并公开窄的 `commands`、`queries` 和 `events`。它是能力的事实 owner，不等同于产品能力本身。

Feature 不得：

- 直接编排其他 Feature；
- 依赖 HTTP、React 或具体 Adapter；
- 决定跨 Feature 删除、恢复或补偿顺序。

### Application：完整动作

Application 表示一个可由多个入口复用，或需要跨 Feature、权限、锁、补偿或生命周期控制的完整业务动作。它拥有输入事实校验、admission、锁顺序、Feature 调用顺序、补偿和错误传播。

不是所有 Feature command 都需要 Application。单一 Feature、单一入口且不需要这些跨边界规则的简单写操作，留在 Feature command；只有满足前述条件时才提升为 Application。

### WorkbenchCoordination：跨能力生命周期

WorkbenchCoordination 只拥有跨 Feature 关系、删除、重连、迁移和恢复流程。它不拥有普通 Feature 数据，也不应成为所有业务 command 的总入口。

### Adapter：外部入口

Adapter 只负责解析外部输入、调用一个窄 command/query、映射结构化错误和返回 DTO。Route 不直接访问 Repository/SQLite，不实现补偿或状态机。

### Projection：事实投影

Projection 只把权威 Feature/Application 事实投影成 Panel DTO 或失效通知。Projection 不能反向成为业务事实源。

### Composition：能力组合

Composition 只负责创建能力所需对象、显式注入依赖、注册 Adapter、调用 `ready` 和 `release`。Composition 不执行业务判断，也不成为新的业务总管。

## 3. 能力组合规则

`PanelHost` 是进程级组合根，但不是 service locator。它只负责创建、连接、注册、启动和释放；不提供业务语义。新能力不得通过字符串从 Registry/Container 取依赖，也不得把完整 `PanelHost` 传给 Route 或 Feature。

使用显式 typed builder 组合能力：

```ts
const feature = createProjectUnderstandingFeature({ workspace, knowledge });
const application = createProjectUnderstandingApplication({ feature, admission });
const routes = createProjectUnderstandingRoutes({ application });
```

不引入动态插件、通用 `FeatureModule`、字符串 Registry/Container、自动扫描、`unknown[]` 聚合协议或自动生命周期推断。能力是编译时集成、强类型、显式依赖的产品能力，不是运行时发现的插件。

`src/app/panel-server/composition/` 只表达组合责任。基础能力可以继续复用已有 Feature 实现，不因为产品能力扩展而全面重写。

## 4. 稳定内核与 canonical path

当前 v1 的稳定内核包括基础 Feature、Repository、Ordinary Runtime、文件身份与授权、删除语义和数据基线。稳定表示默认不重构长期语义，而不是禁止修改：可以修复确定性 bug、增加窄接口；改变 owner、事实、命令语义、删除语义或状态机必须在同一变更中更新架构基线并说明影响。

新能力必须优先组合稳定内核的公开 contract。旧入口如果仍需保留，只能解析输入并委托 canonical command；不得与新入口并行维护第二套 admission、锁、授权、补偿或错误语义。不存在永久双入口、双事实源或双业务实现。

`PanelHost` 的既有扁平字段不是新能力的扩展 API。新代码只能依赖 typed composition 和窄 contract；已有调用方可以在所属能力收敛时改造，但不得新增同类依赖。

## 5. 写入和 admission

涉及 Space、Workspace、Reference、文件或 Knowledge 关系的写操作，必须使用所属 owner 的 admission。`assertAvailable` 只能作为快速失败检查，不能替代锁内重新验证的 `admit`。

需要 owner admission 的能力 mutation 顺序固定为：

```text
获取 owner admission
→ 解析锁键并获取路径锁
→ 重新读取 membership / mount
→ 重新解析 source identity / mountVersion
→ 授权
→ I/O
```

删除、重连和普通 mutation 必须处于同一锁域。Run 冻结授权下的普通文件工具不额外取得 owner admission，但必须在路径锁内重验授权和来源。任何入口都不得反向先持有路径锁再等待 owner admission；否则未来的删除/移动和写入会形成相反锁序。移除引用后，旧请求不能继续写入。

Space 与 Workspace 的 admission 保持显式类型，不把 owner 压缩为字符串：

```ts
spaceAdmission.admit(spaceId, operation);
workspaceAdmission.admit(workspaceId, operation);
```

## 6. 能力接入清单

新增产品能力或跨 Feature 用例前必须回答：

1. 产品能力的名称和边界是什么？
2. 唯一事实 owner 是谁？哪些事实不由它持有？
3. canonical command/query 是什么？入口是 Feature、Application 还是 Coordination？
4. 哪些角色适用：Repository、Application、Coordination、HTTP、Agent、Projection、Migration？
5. 是否需要 admission、锁、revision 或幂等键？
6. 失败、重试和恢复语义是什么？
7. 由哪个 Composition builder 创建和释放？
8. 是否需要更新架构基线、schema/migration 或 backup？
9. 是否属于数据、权限、删除、并发或发布变更，需要最小的真实不变量验证？

## 7. 不过度设计的边界

低概率且低损失的情况可以先使用明确失败和人工重试，不提前构建通用插件、动态 IoC、自动扫描或每个对象的独立 journal。

但以下内容不能因为少见而省略：数据删除与写入竞态、文件授权失效、重复提交、旧请求覆盖新事实、以及 durable mutation 的 revision 冲突。

判断标准是失败损失和恢复成本，而不是用户能否手动快速复现。

## 8. 验证门禁

能力组合、依赖方向、跨 Feature command、删除、恢复或 admission 变化至少需要：

```text
pnpm check:baseline
pnpm typecheck:panel
pnpm build:panel
git diff --check
```

只有数据、权限、删除、并发或发布变更才补充最小场景验证；覆盖真实不变量，不测试 helper 本身。
