# Synech 开发与维护规则

> 本文是架构基线的执行手册。架构基线定义“系统是什么”；本文定义“以后怎么改”。

## 1. 先判断改动属于哪一类

开始改代码前，先回答三个问题：

1. 这是已有 Feature 内部行为，还是跨 Feature 用例？
2. 这是领域事实变化，还是展示/适配变化？
3. 这是一次性启动步骤，还是用户/Agent 可重复执行的业务命令？

判断结果决定入口：

| 类型 | 唯一入口 | 典型例子 |
| --- | --- | --- |
| Feature 内部行为 | Feature command/query | 修改 Note、更新 Space 标题 |
| 跨 Feature 业务 | `app/application` 中的 Application command | 提交 Conversation、创建 managed folder |
| 跨 Feature 生命周期 | `app/workbench-coordination` | 删除 Space、删除 Workspace、重连 Workspace |
| 只读组合 | Read Model / Query facade | Space 页面同时显示引用和 Conversation 摘要 |
| 启动初始化 | Bootstrap/Host startup | 创建默认 Space、初始化 Product Home |

启动初始化不等于用户业务命令，不能因为两者都创建了文件就复制同一套入口。

## 2. 同一个业务动作只能有一个实现

用户、Agent、HTTP、Desktop 或 CLI 如果执行的是同一个业务动作，必须调用同一个 Application command。

正确形态：

```text
HTTP adapter ─┐
Agent adapter ─┼─> 同一个 Application command
Desktop adapter┘
```

禁止出现：

- HTTP 自己创建目录，Agent 再自己创建一次；
- 用户入口有补偿逻辑，Agent 入口静默忽略补偿失败；
- 一个入口检查 admission，另一个入口直接写 Feature；
- 为了“方便”在第二个入口复制 Application 内部步骤。

Application command 必须在一个地方拥有：

- 输入事实校验；
- owner/admission 检查；
- 锁顺序；
- Feature command 调用顺序；
- 失败补偿；
- 错误传播；
- actor/audit 事实。

## 3. Application 和 WorkbenchCoordination 不要混成一个总服务

`app/application` 是一个个专业业务窗口；`app/workbench-coordination` 是跨 Feature 生命周期协调层。

推荐的组合方式：

```text
ApplicationRuntime
├─ ordinaryTurnApplication
├─ managedSpaceFolderApplication
└─ workbenchCoordination
```

规则：

- Application command 只负责一个完整业务用例；
- WorkbenchCoordination 只负责跨 Feature 关系、删除、重连和恢复；
- 不要把所有业务 command 都塞进 WorkbenchCoordination；
- 不要让所有操作共享一条无差别的全局队列；
- 同一个 Application 实例由 Composition Root 创建一次，再注入各个 adapter；
- Application 之间通过窄 port 依赖，不导入具体 Repository、HTTP 或 React。

如果一个 Application 需要被 HTTP 和 Agent 同时使用，应把它放入稳定的 Application Runtime，而不是在 Route 内创建。

## 4. Route 和 PanelHost 的纪律

### Route

Route 只做：

1. 解析 HTTP 输入；
2. 转换为 Application/Feature 输入；
3. 调用一个 command 或一个 read-model query；
4. 把结构化结果映射为 HTTP 响应。

Route 可以组合多个只读查询来生成页面 read-model，但不能自己完成多个 Feature 写入、失败补偿或状态转换。

### PanelHost

PanelHost 是 Composition Root，只负责：

- 创建 Feature、Repository、Application 和 Coordinator；
- 注入依赖；
- 连接事件和 shutdown；
- 持有进程级资源。

PanelHost 不负责：

- 判断业务 owner；
- 决定删除顺序；
- 直接操作 SQLite/文件；
- 在 adapter 之间复制业务策略。

新增对象优先进入对应的 composition builder，不要持续向 PanelHost 增加业务字段和分支。

## 5. Feature 和依赖方向

- 每个长期事实只有一个 owner；
- Feature 只能依赖自己的 Repository port；
- `spaces`、`workspaces`、`personal-knowledge` 不得彼此直接 import；
- 跨 Feature 关系只能经过 Application/WorkbenchCoordination；
- 共享类型放在窄 contract/domain port 中，不要为了复用类型导入整个 Feature/index；
- adapter 可以依赖 Application contract，Application 不得反向依赖 adapter；
- Memory 只按 Space/Workspace owner 保存历史认识；全局只有一个默认关闭的 `enabled` 开关，不提供 Space participation，不保存 global 长期文档或跨项目自动学习。Memory command 收敛为 `setEnabled`、`setRollout`、`clearMemory`、`updateMemory`、`getStatus`、`getMemoryView`；其中 `setRollout` 仅用于开发/装配控制，不扩大用户记忆策略；
- AgentNotes 与 PathDependency 已退役，不得作为当前 owner、命令、持久化目录或兼容层重新引入。Knowledge 用户笔记和现有 Skills 不因此改变；
- CollaborationRules 只记录用户明确要求长期生效的协作依据。全局/Space 文本由 Product Home 管理；Workspace 根 `AGENTS.md` 是该项目规则的唯一事实源，不复制为内部 `RULES.md`，不做嵌套继承。Workspace 规则 mutation 复用 owner admission、身份检查与共享 mutation lock，锁内重验 `mountVersion`、`sourceIdentity` 和 expected-version CAS；删除 Workspace 登记不删除外部规则文件。

### Memory 内部维护边界

以下约束用于内部维护收敛，不改变既有 owner、公共业务命令、schema、状态机或行为；文档约束不代表对应改动已经完成或产品效果已经成熟。

- **分开产品入口与宿主装配。** `memory/index.ts` 只暴露稳定产品 contracts 与 facade；`memory/composition.ts` 是宿主组合根使用的 factory 入口。业务 Route/UI 不得依赖 composition 或 `store`、`capture` 内部实现；UI 继续只消费 Panel API DTO / `ui-read-model` facade。
- **共享预算与计数。** `policy/maintenance-limits.ts` 统一后台预算和重试常量；`token-counting.ts` 统一实际 tokenizer 计数，不用字符估算替代。Admin 依赖共享政策与计数，不依赖 `capture/consolidation`。
- **按职责收口整理管线。** `capture/consolidation` 只编排证据读取、模型调用、重试与发布；提示词构造和输出解析/校验放在纯模块中。不另建工作流引擎，不按每个函数机械拆文件。
- **保留事务内聚性。** 来源、产物、进度与任务状态的原子一致性由现有 Repository 事务保护；不因拆模块把原本同一事务拆为独立提交，不创建第二套 Memory runtime、SQL owner 或长期事实源。
- **发布边界是最终权威。** Background 的最终有效供给统一由 `documentRepository.getSupplyableMemoryRevision` 在原子快照中核验，其他层仅投影/装配，不复制准入算法。Capture 的索引写入、任务登记与整理发布仍在各 Repository 事务内复核政策、generation 和授权排除范围；异步操作之前的预检不构成发布许可。
- **复用核心证明。** 保留已有 owner 隔离、关闭/清除后迟到结果拒绝、用户编辑冲突、分支失效与恢复场景；先复用既有核心测试，仅对未覆盖的真实不变量补最小场景，不为纯重构增加调用次数或镜像实现测试。
- **纠正当前契约，不改写历史。** 当前契约和注释不得继续描述“仅 Space 可用”或“索引不依赖 consent”；它们应与 Space/Workspace 范围、全局开关和授权排除边界一致。历史 ADR 保留当时决策，不把旧设计描述当作当前实现承诺。
- **让边界可检查。** `pnpm check:baseline` 检查产品入口是否泄漏装配或维护实现、Route/UI 是否绕过公开入口，以及 Admin/历史查询/诊断是否重新依赖整理编排。不得用新增 allowlist 掩盖可直接修正的依赖。

### Memory 条目与来源维护（2026-10-03）

[ADR 0019](adr/0019-autonomous-memory-and-provenance.md) 已 Accepted。`entry-contracts.ts` 与现有 Repository 接口共同表达条目、修订和供给，旧整文写入已退役；不存在单独的 Target 仓储或第二套运行时。独立开发验证不等于真实模型质量评测或正式发布。

- 当前不开发向量、嵌入配置或查询时第二 Agent。使用 SQLite FTS5/BM25、少量主题和一跳 related；不引入评分、自动过期、复杂分类或第二运行时。
- MemoryDocumentRepository 唯一事务拥有条目、不可变修订、真实来源、派生 MemoryOwnerDoc 概览、summary、进度与 job 收敛。概览没有 UI 独立写权；updateMemory 写明确条目，使用 head CAS 与 requestId/payload 幂等，不保留整文/条目两套产品编辑路径。
- 普通会话删除保留此前合法发布认识，fence 拒绝在途补记，source 标 deleted 并清理原文索引/辅助 summary。分支替换只将超出保留前缀的来源范围标 superseded；涉及退役来源的修订保守暂停当前供给而保留历史，不猜反证、不自动回退 head。来源 revision/generation 防止同 ordinal 新 Run 自动复活旧来源。clear/owner delete 仍 purge 并防回填。
- 固定概览普通发布不换绑；用户 correction/withdrawal 精确撤销旧 revision 及依赖概览。动态来源状态由最终 Repository 边界核验，不能固化进概览正文或由缓存掩盖。默认当前查询，历史结果标历史角色与当前 revision。
- 后台复用 Pi adapter 与既有辅助 generate。相关条目初始输入及 search_entries/read_entry/read_evidence 窄读取只限 job owner、授权证据与共享预算，有限 continuation，无通用工具权限。原文缺失与原因未知不造补，occurred/reported/published 时间分开。
- 调整存储时直接修改当前 version 1 目标结构，并同步更新数据基线、核心验证、模型说明和 UI。不改 package/data version、不兼容旧开发数据、不在启动重置。普通关服、failed-start 和恢复备份共用记忆释放入口，排空在途采集/整理后才关闭共享数据库。
- 工具结果的正文、适用范围、原因和来源均参与同一预算及续读协议，不能只裁正文然后跳过未返回内容。单条目最多 4 个主题和 3 个直接关联；主题最多 4 个别名。来源数量可增长，查询通过来源分页与状态总计保持可读。
- 当前不增加向量配置、模型下载、占位索引或开源引擎专属类型。后续增强依靠稳定内容身份/版本、统一查询口和可重建索引适配；不开启增强也能完整使用记忆。查询时委托记忆 Agent 仅记录为实验方向，不属于当前实现。

### Agent Runtime Provider 边界

- pi-agent 只作为底层 Agent Runtime Provider；Synech 产品层通过自己的 Agent Runtime Port 使用它。
- `AgentHarness`、`AgentLane`、pi `Session`、pi `Context`、`HarnessEvent`、pi operation/entry ID 和 pi 工具签名只能出现在 Pi Adapter 内。
- 产品层使用 `conversationId`、`runId`、`turnId`、`toolInvocationId` 和 `checkpointId`；不得把 pi `entryId` 写入产品稳定状态或通过 pi leaf 推导业务状态。
- 普通 Agent 运行的 Provider retry、压缩触发和 Pi transcript 由 pi 拥有；产品取消、审批、权限、账本、工具结果接受、世代撤销和终态由 Synech 拥有。
- Pi commit queue 不能替代 Synech 世代栅栏。撤销某个写入世代后，旧世代未完成的写请求不得继续写入。
- 任何 pi 升级先阅读 [Agent 运行层接入与开发手册](Agent运行层接入与开发手册.md) 和 `adr/0003-agent-runtime-provider-boundary.md`；未完成探针不得直接并入主工作树。

如果为了传一个类型而形成模块环，先抽窄 port，不要关闭 cycle checker 或添加宽泛 allowlist。

## 6. 并发、锁和恢复

需要 owner admission 的引用、生命周期或外部来源 mutation 必须遵守固定顺序：

```text
获取 owner admission
→ 解析锁键并获取路径锁
→ 重新读取 membership
→ 重新解析 source identity/mountVersion
→ 授权
→ I/O
```

规则：

- 锁外读取的 DTO 不构成授权；
- 不得先持有路径锁再等待 owner admission；统一顺序避免删除/移动与文件写入形成反向等待；
- Run 冻结授权下的普通文件工具不额外获取 owner admission，但必须在路径锁内重新验证授权和当前来源；
- unlink/delete/reconnect 与文件 mutation 必须使用同一锁域；
- 不要在一个公开串行 command 内再次调用同一公开 command；需要拆成内部 workflow；
- 删除、恢复、跨存储补偿必须有 durable journal 或等价恢复事实；
- 未知错误必须继续上抛，不能伪装成“没有上下文”“空列表”或成功；
- 只在确实存在跨资源原子顺序时使用协调层队列，避免全局串行化所有业务。

## 7. 数据和 schema

- Repository 读取磁盘/SQLite 后必须运行时校验；TypeScript `as` 不是校验；
- JSON/SQLite 结构变化必须更新 schema、manifest、测试和文档；
- 当前为未发布 v1，`synech/v1` 是稳定目标身份。每个 owner 直接维护一个完整 version 1 目标 SQL/checksum；不为开发改动递增 schema、数据格式或产品版本，不为旧开发数据追加迁移或保留自动兼容链；正式发布前另行冻结用户数据迁移政策（ADR 0006）；
- schema、data format、owner 或删除语义变化必须先写 ADR，在同一变更中更新架构基线，并说明目标结构变化、旧开发库拒绝与恢复影响；
- `synech/v1-baseline-5`、`synech/v1-dev`、未知 namespace、旧 owner 版本和不匹配 checksum 明确拒绝，不改写身份或 ledger。未发布阶段不迁移或抢救旧开发数据；需要清理时由用户明确执行 data-only reset：`pnpm reset:product-home -- --data-only`。脚本取得 Product Home lease、要求确认实际目标路径，只清理 `data/` 与相关 lifecycle state，并保留 `config/`、模型凭据、外部 Workspace 文件和共享工作树；
- 应用启动不得静默删除、重建或降级 Product Home；
- 备份必须明确声明覆盖范围，不得把 Workbench backup 误称为完整 Product Home backup。Backup manifest v3 与 Pi 原生 JSONL V4 是独立格式，不随 SQLite owner version 1 重编号；恢复仍精确校验当前 fingerprint 与 ledger。

调整 SQLite 结构后，先运行 `pnpm build:node`，再运行 `node scripts/update-data-baseline.mjs` 更新目标基线。该命令通过正式启动入口创建临时新库并读取实际结构，不读取或重置用户 Product Home；`node scripts/update-data-baseline.mjs --check` 只校验。共享工作树的 `dist` 构建必须串行协调。架构门禁检查 namespace、`synech/v1`、每个 owner 的单版本定义和 checksum 形态；fresh 基线校验与运行时 ledger 校验负责实际 SQL 一致性，不将旧开发 checksum 冻结为兼容协议。

## 8. 错误、展示和 DTO

- Domain/Application error 描述业务事实；
- Panel/HTTP adapter 把业务 error 映射为状态码；
- Application、Feature、Repository 不应依赖 `PanelHttpError`；
- code、kind、eventType、sectionId、status 负责程序分支；
- title、label、message、detail、summary 只负责展示；
- 不通过本地化文案、正则或字符串前缀恢复状态机；
- 外部输入在 owner 边界解析为结构事实，不能把 `unknown` 直接当领域对象使用。
- 媒体工具通过 `ToolExecutorOutput` 返回显式输出和附件；不要在业务 JSON 上添加隐藏属性或独立的“已附图”事实。文字整理只变换 `output`，图片发送从实际附件生成。持久化与 UI 只消费 durable `ToolCallResult`（ADR 0012）。
- 公共工具政策只解释工具明确声明的参数用途；HTTP 方法审批由 `http_request` hint 指定，URI 协议校验留在执行 adapter。MCP 重连必须重读真实工具目录，冻结契约变化不得沿用旧授权继续执行（ADR 0013）。

## 9. UI 状态边界

新增 UI 功能时，优先按三层组织：

```text
Feature API Client
→ Server State / Store
→ Component
```

- API Client 负责请求、DTO 和 API error；
- Store 负责 snapshot、optimistic mutation、失效和回滚；
- Component 负责渲染和触发动作；
- Server snapshot 是权威事实；
- SSE 只负责失效/增量观察，不取代权威读取；
- 流式 Transcript 使用独立 stream controller，不要强行塞进普通 query cache；
- 会话异步响应在请求开始时捕获 `conversationId + runId + view epoch`；成功、失败、ref 写入、审批/取消忙状态和订阅切换都校验同一身份。相同 run 重建 SSE 后，旧连接回调也必须验证订阅实例，不能关闭或覆盖新连接；
- 新增复杂状态时先写纯函数/headless 测试，不要只依赖浏览器手工点击。

基础交互的日常维护约束：

- 文件、笔记、知识条目、对话列表和当前空间名称不添加重复名称的原生 `title` 提示；图标动作和确有额外信息的路径提示按需保留，无障碍名称继续使用 `aria-label`。
- Panel 文档默认关闭拼写检查；桌面窗口同时显式设置 `webPreferences.spellcheck = false`，新增输入框继承同一默认值。
- 嵌套操作菜单的外部点击按 React 子树识别，包含 Portal 中的内容；不能只用 DOM `contains` 提前卸载菜单。Escape 先关闭当前操作菜单并恢复触发器焦点，再由外层弹层处理后续 Escape。

第三方 UI 库或状态库不是架构本身。引入它们必须解决明确的状态一致性问题，不能为了替换现有代码而替换。

模型设置的日常维护约束：

- 浏览中的服务与运行时活动服务分别由页面选择和权威配置决定；异步保存不能重新导航或覆盖后来输入的表单。
- 编辑草稿只能投影已有连接，创建草稿才可新增身份；明确清空的字段不得回退为旧值，已删除连接的迟到编辑不得重新加入列表。
- 删除执行前读取当前配置；切换备用服务或删除部分失败后重新读取配置。设置页呈现失败并保留当前编辑，不将本地乐观回滚当作服务端事实。
- 有搜索词时保留清除入口。服务详情只使用一层纵向滚动，切换连接重置详情滚动位置并保持列表可访问。

## 10. 验证

测试不是每次改动的默认交付项。小功能、样式、文案和低风险优化优先做相关类型检查、构建或人工验证；不要为了覆盖率新增镜像实现的测试。

只有用户明确要求，或改动涉及数据、权限、删除、并发或发布阻断时，才写最小必要的验证。此时覆盖正常路径及实际会造成数据错误或不可恢复结果的失败路径即可，不扩展成全套测试工程。

交付前按改动范围执行：

```text
pnpm check:baseline
pnpm typecheck:panel
pnpm build:panel
git diff --check
```

不要只报告“TypeScript 编译通过”。高风险变更仍须说明 owner、失败、并发和恢复语义。

## 11. 架构基线更新触发条件

出现以下任意情况，在同一变更中更新架构基线并说明影响：

- 新增或替换 owner；
- 新增公共 Application command；
- 修改删除语义或状态机；
- 修改 Product Data Format、schema 或 migration；
- 修改 Conversation owner 规则；
- 引入新的运行时、持久化类型或跨进程协议；
- 改变模块依赖方向；
- 把当前本地单用户模型扩展为远程/多用户模型。

通常不需要更新架构基线的情况：

- Feature 内部实现优化且不改变契约；
- 修复同一政策函数的边界 bug；
- 纯展示样式或不改变结构事实的文案调整。

## 12. 提交和交付纪律

- 一个提交只包含一个逻辑切片；
- 共享 dirty worktree 中不属于自己的文件不得覆盖、清理或顺手提交；
- 提交前检查 `git diff --cached --name-only`；
- 新增文件、删除语义和数据格式变化必须在提交说明中明确；
- 高风险变更所需的验证、文档、类型契约和实现应在同一逻辑切片中更新；
- `git status` 干净不是完成定义；按风险完成必要验证并保持关键不变量才是完成定义。

## 13. 完成前自问

提交前必须能回答：

1. 这个事实的唯一 owner 是谁？
2. 这个业务动作的唯一入口是什么？
3. HTTP、Agent、Desktop 是否复用了同一个 Application command？
4. 失败、重试、并发和恢复是否复用了同一政策函数？
5. 是否引入了新的字符串协议、平行 DTO 或隐式兼容？
6. 是否把业务逻辑放进了 Route、PanelHost 或 UI 组件？
7. 这是否是高风险改动；需要哪些最小验证与基线更新？
8. 当前提交是否混入了其他 dirty worktree 的改动？

## 对话资源与分支维护

- 模型徽标来自内置资产与稳定身份，禁止把展示图片冻结进 Run。Run 只保留所选模型的配置；审批、工具结果、能力契约与恢复 checkpoint 属于必须持久化的运行事实。
- 离线运行存储整理：先完成构建，退出占用该 Product Home 的桌面端与服务，再执行 `pnpm compact:run-storage`。命令取得 Product Home lease、校验全部快照、备份实际重写的文件，拆分不变 birth 与动态 snapshot、移除默认诊断与重复 capabilityResolution，保留 Run revision；默认不清理 Pi transcript 或 Chromium 缓存。恢复备份仅留本地，不进入版本控制。
- 消息编辑界面只提供紧凑操作，不常驻解释文字。编辑保留原附件，失败保留编辑草稿；旧版本和后续对话通过分支选择恢复；不提供独立回退或撤销/重做入口（ADR 0017）。
- 分支变化由 Ordinary 单命令持锁执行，临时意图在移动 Pi tip 前落盘；重启根据 Run 出生是否提交完成或回退。外部工具副作用不随 transcript 分支选择撤销。

## 运行性能与诊断

- 详细工具统计须在开发者模式中显式开启，新提交携带 opt-in，默认不创建 collector。历史运行不因打开诊断视图补录；普通计费 usage 继续保存。
- Ordinary Run 的 immutable birth 与 mutable snapshot 使用同一 owner/入口；状态变化不得重写 birth。Pi Session 复用必须有容量和闲置边界，并保留 writer generation 撤销、文件修改失效及 shutdown 关闭。
- 消息版本切换的 HTTP 响应是当前权威会话；禁止收到后再发同一个会话 GET。可见历史先复用已有 activity cache，缺失详情后台补齐；请求 epoch 必须隔离跨会话和旧响应。
- 会话目录用 `listConversationSummaries`；不构造全部正文或完整运行视图。MAX_SAFE_INTEGER 仅表示读取完整 manifest，不再作为强制文件扫描协议；恢复显式检查并修复 inventory。
