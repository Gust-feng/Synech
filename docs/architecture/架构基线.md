# Synech v1 架构基线

> 状态：v1 release baseline
> 适用范围：Windows、本地单用户、运行时强制单 Product Home / 单 PanelHost、仅 loopback API

本文是 Synech 稳定概念、所有权和工程门禁的最高事实源。[开发维护规则](开发维护规则.md) 负责把这些事实转成日常开发纪律。Handbook 负责解释实现；实现、测试或 Handbook 与本文冲突时，必须在同一变更中完成收口，不能长期保留双重事实。

## 1. 产品与领域事实

| 概念 | 定义 | 权威 owner | 不拥有 |
| --- | --- | --- | --- |
| Space | 通用长期组织空间 | SpaceFeature | Workspace mount、外部文件内容、Knowledge 内容 |
| Workspace | 真实目录的稳定登记身份 | WorkspaceFeature | 目录内用户文件、Space membership |
| Knowledge | 长期沉淀的 Note/Page/Theme/Link | PersonalKnowledgeFeature | Space 生命周期、外部来源 |
| Conversation | 固定归属一个 Space 或 Workspace 的对话 | Ordinary | 浏览页面、临时 cwd |
| SpaceReferenceItem | Space 对外部或托管资源的一次 membership | SpaceFeature | 被引用对象自身生命周期 |
| AgentNotes | Agent 运行中明确读写的运行事实与笔记 | AgentNotesFeature / Ordinary 运行命令 | 隐式 Memory、用户显式规则 |
| CollaborationRules | 用户明确维护的全局、Space、Workspace 协作规则 | CollaborationRulesFeature | AgentNotes、隐式 Memory、原始对话 |
| PathDependency | 可复用的方法、流程和适用条件 | PathDependencyFeature | 隐式 Memory、原始对话 |
| ImplicitMemory | 从稳定对话派生的会话总结、Space 长期文档、来源、进度和后台任务 | MemoryFeature | 原始 Conversation、owner 身份、显式规则 |

稳定规则：

- Space reference 直接保存 `workspaceId`；关系身份是 `SpaceReferenceItem.id`，不存在第二套 WorkspaceLink。
- Workspace owns `workspaceId + mountVersion + sourceIdentity + status + visibility`。
- Knowledge Note 的 `spaceId` 是可选组织关系；Space 删除只解除关系，不删除 Knowledge-owned 内容。
- Conversation owner 创建后不可改变；上下文附件和 cwd 不能改变 owner。
- 外部用户文件默认不由 Synech 删除；managed content 必须走 owner 的 durable deletion lifecycle。
- CollaborationRules 的 durable 文本位于 Product Home 的 `data/memory/collaboration-rules`，通过 `CollaborationRulesApplication` 的 CAS 命令写入；不得借 AgentNotes 或 Memory 的文件代替。
- ImplicitMemory 的文档、来源、进度、任务和检索投影位于同一 Product Home SQLite，由 `MemoryAdminApplication`、Capture/Background/HistoryQuery Port 和 WorkbenchCoordination 的 lifecycle 入口管理。

## 2. 分层和依赖

```text
Panel UI -> Panel API DTO / 明确的 ui-read-model facade
Panel Route -> Feature command 或 WorkbenchCoordination command
WorkbenchCoordination -> Feature contracts
Feature -> 自己的 Repository port
Repository adapter -> SQLite / filesystem
```

- `spaces`、`workspaces`、`personal-knowledge` 不得彼此直接依赖。
- 跨 Feature use case 由 `app/workbench-coordination` 拥有。
- Coordinator 不依赖具体 Repository、SQLite、HTTP 或 React。
- Route 不创建 Feature、不访问 Repository、不直接组合两个 Feature command。
- PanelHost 是进程组合根，不是供任意调用点读取内部对象的 service locator。
- Panel UI 不直接导入 `panel-api/read-model`；只允许 Panel API DTO 和明确审查为 client-safe 的 `ui-read-model` facade。

## 3. 应用命令基线

跨 Feature 行为只有以下入口：

```text
attachWorkspaceToSpace
detachWorkspaceFromSpace
reconnectWorkspace
hideWorkspace
deleteWorkspace
deleteSpace
detachKnowledgeFromSpace
```

记忆相关的唯一公开入口：

```text
MemoryAdminApplication.setRollout / setConsent / setSpaceParticipation / clearImplicitMemory / writeSpaceMemory / getSpaceMemoryView
MemoryFeature.queries.getDiagnosticSnapshot / searchDiagnosticHistory
CollaborationRulesApplication.get / write / delete
```

Panel Route 只能解析输入、调用其中一个入口并映射错误；不得在 Route 或 UI 中组合文件、SQLite、admission 或删除步骤。

命令语义：

- attach 复用相同 source identity 的 Workspace；新建 implicit Workspace 后若 membership 写入失败，且对象没有引用/Conversation，则补偿清理登记。
- detach 只移除 Space membership，不删除 Workspace 或真实目录。
- reconnect 必须验证相同 source identity，并与所有 active Workspace 根执行重复/父子嵌套检查。
- hide 只修改 visibility；永久 delete 是独立危险操作，删除软件登记和 owner 数据但永不删除真实目录。
- delete Space 清理 Space-owned 数据并解除 Knowledge 来源/组织关系；Knowledge-owned 内容保留。

## 4. 身份、授权和并发不变量

- local file 和 Workspace mount 在每次 I/O 前验证当前来源身份。
- 需要 owner admission 的引用/生命周期 mutation 顺序固定为：owner admission -> 解析并获得路径锁 -> 重新读取 membership -> 重新解析 source identity/mountVersion -> 授权 -> I/O。Run 冻结授权下的普通文件工具不额外取得 owner admission，仍在路径锁内重验授权和当前来源。任何入口都不得先持有路径锁再等待 owner admission。
- unlink/delete 与文件 mutation 使用同一锁域；锁外保存的 DTO 不构成授权。
- 首次注册、ensure、reconnect、startup validation 共用同一 Workspace mount policy。
- catch 只能处理声明过的错误 code；Repository、Feature released 和未知错误必须继续上抛。
- Feature 内 read-modify-write 经过唯一串行入口；跨 Feature command 经过协调层串行入口。
- Memory 的 Recall 是可选贡献：Recall deadline 或 Memory-owned index 故障只能在 Host optional adapter 边界变成空贡献；共享 Product Home/SQLite 完整性错误必须继续上抛。
- `data/memory` 的文件快照与备份必须共享 Product Home mutation lock；SQLite backup 依赖 SQLite 的一致性快照和事务边界。不得在持有共享存储锁时等待 per-record/per-owner 队列，避免反向等待。
- PanelHost 在打开任何 Product Home 存储前必须取得 OS-owned runtime lease；同一 Product Home 的第二个进程明确失败。
- Desktop 使用 Electron single-instance lock，并把二次启动聚焦到已有窗口；Panel API 拒绝非 loopback host。

## 5. 数据基线

当前正式数据格式为 `synech/v1`：

- Repository 的 version 1 是冻结的新建库定义；fresh Product Home 的 schema fingerprint 必须等于 `docs/architecture/data-baseline.json`。
- 唯一自动兼容入口是已发布 v1.0.1 的精确身份和完整 migration ledger：`synech/v1-baseline-5 -> synech/v1`。升级在一个 SQLite `BEGIN IMMEDIATE` 事务内重建三张历史 DDL 不同的表、保留其内容、归一 migration ledger 后更新身份；任一步失败必须 rollback。
- `synech/v1-dev`、不完整/篡改的 v1.0.1 ledger、未知 namespace 或其他旧格式一律明确拒绝。启动不得静默删除、重建、降级或把身份标记改写为兼容；用户需要先备份，再显式 reset。
- 此后已存在 migration 不得修改、删除或重排；结构变化只能为对应 owner 追加单调递增版本。数据格式、owner、破坏性 schema 或删除语义变化必须在同一变更中更新本文和 ADR，并说明迁移影响。
- Repository 读取磁盘/SQLite 后必须执行运行时 schema 校验，不能用 TypeScript `as` 代替。
- Backup manifest v3 覆盖 `knowledge-assets`、`space-files` 和 `memory-data` 三个 durable root；v2 及更早 manifest 不属于当前 v1 恢复格式，恢复入口必须明确拒绝，不能静默丢失记忆规则或路径依赖。

## 6. 显示与错误基线

- Workbench 默认使用目录与单内容区；协作入口仅位于已打开预览的路径/工具栏，由用户显式开启，普通导航、提交和恢复不得自动开启。全局导航与文件目录分别控制，选中文件只切换阅读，不得隐式收起任一导航；打开协作时收起全局导航以让出阅读宽度，文件目录收放保持不变，结束协作回到阅读也不自动展开全局导航。浏览选择与活动 Conversation 独立，但右侧会话面板只投影当前所选 Space/Workspace owner 的会话；切换 owner 时不得显示前一 owner 的正文、运行状态或历史条目。分栏、目录收放和浏览导航不得改写 Conversation owner 或隐式扩大上下文授权。
- 单栏由普通布局占满内容区，隐藏面板脱离文档流；分栏实例只在协作时拥有尺寸，退出时同步释放。动画只负责呈现，不持有第二份布局模式或异步提交权。预览工具栏铺满当前面板，正文阅读限宽只作用于正文。
- code、kind、eventType、sectionId、refs 和状态机负责程序分支。
- title、label、message、detail、summary 只负责展示；不得通过字符串比较、正则或本地化文案恢复业务语义。
- UI 乐观状态必须能被权威 HTTP snapshot 覆盖；SSE 只负责失效和增量观察。
- 未知错误如实保留 cause；不得伪装成空状态或静默省略上下文。

## 7. 变更等级

| 变更 | 要求 |
| --- | --- |
| Feature 内实现，不改变契约 | 相关类型检查、构建或人工验证 |
| 跨 Feature command、状态转换、不变量 | 更新基线/Handbook；按风险补充最小验证 |
| owner、公共 API、数据格式、删除语义 | 基线更新、明确迁移/恢复语义，并做最小必要验证 |
| 新运行时或替换 Ordinary/Tool Center | 单独产品决策，不得顺手实施 |

## 8. Definition of Done

一个变更只有同时满足以下条件才完成：

1. owner、唯一写入口、关系身份和失败语义明确；
2. 正常、失败、重试、并发、恢复路径复用同一政策函数；
3. 外部输入在 owner 边界解析为结构事实；
4. 数据、API、UI 投影和文档没有第二事实源；
5. 高风险数据、权限、删除、并发或发布变更有针对真实不变量的最小验证；其他改动不默认新增测试；
6. `pnpm check:baseline`、相关 Panel typecheck/build 和 diff check 通过；
7. 当前逻辑切片不混入无关 dirty files。
